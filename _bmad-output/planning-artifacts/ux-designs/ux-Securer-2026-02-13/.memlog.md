topic: Securer UX — visual identity and experience contract
updated: 2026-09-07T13:04
---

- (event) UX run reconstructed from ux-design-specification.md during the v6.0.3 to v6.12.0 migration; the single spec is split into the DESIGN.md / EXPERIENCE.md spine pair
- (decision) visual register is clean futurism — whitespace-dominant, typography-led, no UI chrome; references are Google Search (single focal point), Apple product pages (type-first hierarchy), Linear (polished developer tool)
- (decision) trust is treated as a visual-quality problem: a recipient judges an unfamiliar link in about five seconds before reading anything, so investment goes into type, spacing and restraint
- (decision) security theater rejected outright — no shields, padlock badges or military-grade claims; overcompensating imagery costs trust rather than earning it
- (decision) dark/terminal aesthetic rejected: it alienates the non-technical recipient the product depends on
- (decision) single accent colour indigo #6366F1, chosen for the intersection of modern tech and trustworthy institution (Linear, Stripe docs, Vercel register); avoids legacy enterprise blue and trend colours that date
- (decision) amber reserved exclusively for irreversible destruction, red rationed to incorrect password and validation only
- (decision) dead-end screen deliberately carries no semantic colour — it is a neutral terminal state, not an error; treating it as an error would make routine ephemerality feel like a malfunction
- (decision) two font families: Inter for interface text, JetBrains Mono for all user data (secret input, revealed secret, generated URL) — the mono switch is semantic, telling a developer their content is verbatim
- (decision) generous corner radii (10px inputs, 24px glass card) chosen for emotional reasons: sharp edges read institutional and hostile, which is what stops a non-technical recipient typing a password
- (decision) chosen design direction is a hybrid of direction 3 (split layout) and direction 4 (floating glass) from the eight explored in mockups/design-directions.html
- (decision) split layout solves the trust problem by keeping the security explanation visible without competing with the form; the gradient panel is dropped entirely below 768px
- (decision) recipient surfaces stay centred and minimal with no glass treatment — single-task screens where clarity beats material
- (decision) backdrop-filter treated as progressive enhancement behind @supports with a solid-white fallback; the glass is never load-bearing
- (decision) design system is Tailwind plus shadcn/ui over Radix — chosen because it produces no recognisable framework look, and Radix supplies keyboard and screen-reader behaviour for Dialog and Select
- (decision) three surfaces only (sender, recipient, dead end) with no navigation; the dead end is a state of the recipient route, not a fourth route — that is what makes FR-21/FR-22 achievable rather than aspirational
- (decision) state advances in place without pushing history, so the back button never lands a user in a half-finished flow
- (decision) auto-copy on generation is paired with a mandatory visible manual-copy fallback, since browsers may refuse a clipboard write outside a user gesture
- (decision) confirmation before reveal survives the password-in-link path — convenience mode removes the prompt, never the warning
- (decision) attempts-remaining counter appears only after the first failure; showing a budget on arrival frames a legitimate recipient as a suspect
- (decision) validation fires on submit rather than blur — speed over handholding; only secret text and password are required, everything else defaults
- (decision) dead-end copy frozen at one sentence with no cause given; noted in EXPERIENCE.md as the most likely future regression, because the instinct to be more helpful here is a security defect
- (decision) no onboarding anywhere: a recipient has zero context and owes the product nothing, so every screen teaches itself or fails
- (decision) accessibility floor is WCAG 2.1 AA; visual contrast owned by DESIGN.md, behavioural floor (keyboard, semantics, announcements, targets, motion) owned by EXPERIENCE.md
- (decision) motion is functional only and prefers-reduced-motion switches instantly rather than shortening
- (event) spines finalized; DESIGN.md carries frontmatter tokens per the Google Labs design.md spec, EXPERIENCE.md cross-references them by token name and both win over any mock
